# 테스트 규칙

## 테스트 우선순위

테스트는 코드 커버리지가 아닌 제품 리스크를 따른다.

### 가장 높은 우선순위
- 규칙 기반 필터링 동작
- 평가 상태 전환
- 피드백 저장 및 메모리 요약 동작
- 구성 로딩 및 환경 분리 안전장치
- `X-API-Key`를 사용한 파이프라인 트리거 인증

### 두 번째 우선순위
- LLM 구조화된 출력의 파싱 및 검증
- Slack 페이로드 포맷팅 및 웹훅 처리
- 스크래퍼 정규화 및 중복 제거 동작
- 대시보드 응답 형태 만들기

### PoC에서 낮은 우선순위
- 광범위한 UI 스냅샷 커버리지
- 존재하지 않는 플랫폼 스크래퍼의 철저한 테스트
- 단순한 프레임워크 연결을 위한 가치 없는 단위 테스트

## 테스트 형태 지침

- 순수한 로직은 빠른 단위 테스트로 먼저 배치한다.
- DB 기반 흐름 및 API 핸들러에 통합 테스트를 추가한다.
- LLM 출력 및 Slack 페이로드에 계약 테스트를 추가한다.
- 스크래퍼는 고정 데이터(fixture) 기반 파싱 테스트를 선호한다.
- 필터링, 점수 매기기, 피드백, 중복 제거의 모든 버그에 회귀 테스트를 추가한다.

## 최소 요구 사항

- 의미 있는 모든 기능 개발에는 자동화된 테스트가 포함되어야 한다.
- 새로운 비즈니스 로직은 최소한 하나의 테스트와 함께 제공되어야 한다.
- 버그 수정에는 회귀 테스트가 포함되어야 한다.
- 테스트를 건너뛰는 경우 이유를 문서화한다.

## 완료 조건 (Definition of Done)

기능이나 버그 수정은 다음이 모두 포함될 때 완료된다:

1. 구현 코드
2. 자동화된 테스트
3. 문서 또는 계약 업데이트 (동작/인터페이스 변경 시)
4. 운영 문서 업데이트 (`/internal`에서 확인해야 하는 상태가 바뀌는 경우)
5. 환경 변수 또는 구성 템플릿 업데이트 (설정 변경 시)
6. 로깅 및 오류 처리 검토

## 테스트 구조

```
tests/
  unit/          -- 빠른 단위 테스트 (순수 로직)
  integration/   -- API 및 파이프라인 통합 테스트
  contract/      -- LLM 출력, Slack 페이로드 계약 테스트
  fixtures/      -- 테스트 데이터
  conftest.py    -- Pytest 전역 픽스처
```
