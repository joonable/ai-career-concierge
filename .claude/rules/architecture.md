# 아키텍처 규칙

## 시스템 계층

프레젠테이션, API/오케스트레이션, 에이전트 파이프라인, 스토리지 계층 간에 시스템을 느슨하게 결합(loosely coupled)하도록 유지한다.

- 평가 파이프라인을 LangGraph `StateGraph`로 모델링한다.
- 스크래핑, 규칙 필터링, LLM 평가, 전달(delivery)은 별도의 관심사로 유지한다.
- 임의의 dict 파싱보다 타입이 지정된 모델과 구조화된 출력을 선호한다.
- 피드백 기반 추천 워크플로우에 맞게 스키마와 API를 일치시킨다.

## 폴더 구조 원칙

TRD의 시스템 계층과 일치하고 경계를 명확하게 유지하는 구조:

- `apps/web` -- Next.js App Router 프론트엔드 (페이지 라우트 `src/app`, UI `src/components`, 연동 `src/lib`)
- `src/api` -- FastAPI 라우트, 오케스트레이션, 인증 및 연동
- `src/agent` -- LangGraph 워크플로우, 프롬프트 빌더, 평가 스키마 및 노드
- `src/scraper` -- Playwright 기반 수집 로직 및 소스별 스크래퍼
- `src/db` -- 레거시 SQLModel 모델, 마이그레이션 기록 및 스키마 참조
- `src/common` -- 공유 설정, 로깅, 상수 및 유틸리티
- `src/promptops` -- PromptOps 거버넌스 모듈
- `tests` -- 단위, 통합, 계약 테스트
- `docs` -- 제품/기술 문서, 운영 문서

## 폴더 규칙

- 모호한 헬퍼 대신 도메인 및 책임별로 그룹화한다.
- 프레임워크 진입점은 가볍게 유지하고 비즈니스 로직은 재사용 가능한 모듈로 밀어 넣는다.
- 일반적인 평가 모듈에 Slack 연동 로직을 두지 않는다.
- 스크래퍼 구현은 소스별로 격리한다 (한 소스의 오류가 다른 소스를 오염시키지 않도록).
- 공유 스키마 및 설정을 여러 계층에 복제하지 말고 예측 가능한 단일 위치에 둔다.

## 모듈 설계 규칙

- `evaluation_service.py`, `slack_notifier.py`와 같은 명시적인 이름을 선호한다.
- `utils.py` 같은 포괄적인 파일 이름은 피한다.
- 프롬프트 빌드 로직은 전송(transport) 또는 제공자 클라이언트와 분리한다.
- API 요청 모델, 도메인 모델, 영속성 모델을 별개로 유지한다.
- 필터링, 점수 정규화, 프롬프트 조립은 순수 함수를 선호한다.

## 구현 지침

- 나중에 확장될 수 있는 단순한 설계를 선호한다.
- 작동하는 수직 슬라이스가 존재하기 전에는 불필요한 추상화를 피한다.
- LLM 사용을 좁고 타입에 맞으며 관찰하기 쉽게 유지한다.
- 실패 경로를 명시적으로 만든다.
- 스크래퍼, LLM, Slack 연동을 테스트에서 모킹할 수 있도록 이음새(seams)를 추가한다.
- 새 영속성 작업에는 Supabase Data API 경로를 선호한다.
- 작업 결과를 UI에서 검증 가능한 형태로 수직 슬라이스를 마무리한다.
- `/internal` 운영 패널에서 운영 가시성을 유지한다.
